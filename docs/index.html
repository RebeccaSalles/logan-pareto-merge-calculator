The Query-Storage Trade-off Calculator

A way to choose how Logan Search's Bloom-filter index merges small per-span sub-indexes, trading storage against query speed without building a single candidate index. It's already been checked against a 16-configuration measurement campaign, and confirming it at full-corpus scale is next.

The problem

Recommend a Merge Configuration, Cheaply

Logan Search's Bloom-filter index over span≤20 is split into many small per-span sub-indexes. Merging them into fewer, larger groups speeds up queries but grows storage, so picking the right (base, groups) combination matters — and whichever one you pick, correctness (no false negatives) is unaffected. The hard part is that testing a candidate for real means building it, and that costs hours of cluster time per attempt.

The deliverable

A cost score

Ranks any candidate design by estimated query cost, using numbers the toolchain already produces. No index needs to be built.

One obvious shortcut is picking the smallest group count that fits the storage budget. That curve comes straight from the toolchain, so it doesn't even need scoring. But it says nothing about query time, and it turns out base moves query cost too, not just group count (see How It Works).

Full explanation of the formula is in the next section, How It Works. Every constant below (4GB per partition, the power-of-2 rounding, the 4–256 caps) is a real, checkable assumption, not a derived one. Change any of them, and the chart and trend charts recompute live from the same real per-group storage data — no need to re-run kmhelpers. Score is only comparable within one formula setting, though: a smaller number after a tweak doesn't mean “better,” just a different scale. What actually matters is whether the ranking or the recommended design changes.

How the Calculator Works

Query time on this kind of Bloom-filter index is driven mainly by how many partitions a query has to open on disk: time ≈ (partitions opened) × disk latency, plus a fixed transfer floor. The calculator turns that into a checkable score using numbers the toolchain already produces, without ever building an index. Every constant here can be edited in the live sandbox at the end of this section.

score(design, L) = Σ_g min( nb_partitions(Sg), M(L) )
Sgstorage size of group g, from kmhelpers profile
nb_partitionsthe group's partition count, from kmhelpers' own compose formula
M(L)distinct minimizers in a query of length L. Since the index shards k-mers by minimizer rather than by k-mer, this is the real bound on how many partitions a query can touch. Computed with kmtricks' own minimizer selection (exact encoding, canonical form, low-complexity filter), k=25, m=10:
query lengthM(L)
250bp26 (24–29)
500bp54 (47–61)
1000bp112 (103–122)

ALGORITHM QueryStorageTradeoffCalculator(manifest, base_grid, group_grid, query_lengths) # 1. Enumerate the design space -- real kmhelpers calls, no build designs = [] for base in base_grid: for groups in group_grid: d = kmhelpers.profile(manifest, base, groups) # ~30s, real designs.append(d) # 2. Real per-group partition count (kmhelpers' own compose formula) for d in designs: for g in d.groups: raw = 1 + g.bytes // 4_294_967_296 # 4GB per real partition g.nb_partitions = clamp(round_pow2(raw), 4, 256) # 3. Score per query length -- capped by distinct minimizers M(L) for L in query_lengths: M = distinct_minimizers(L, k=25, m=10) # real, computed for d in designs: d.score[L] = sum( min(g.nb_partitions, M) for g in d.groups ) # 4. Rank -- Pareto frontier over (storage, score), per length for L in query_lengths: frontier[L] = non_dominated(designs, keys=(storage, score[L])) return designs, frontier # -> drives the interactive calculator above

Base affects the score too, through partition count: a higher base merges wider span ranges into each group, which raises its storage and, with it, its partition count. Across the 250 candidates that range runs from 4 to 256 — it isn't fixed. At training scale (Validation, below) groups stay small enough to sit near the floor of 4, which is why base's effect doesn't show up there. Whether it shows up as a measured full-corpus query-time difference is still an open question (Status, below).

How the calculator was checked

The Training Campaign

Building and querying a full index is expensive: at the measured production rate (40 threads, 0.13328 seconds/sample), one full 7.15M-accession build takes on the order of 11 days. So the first check ran on a 60,000-sample subsample instead, where all 16 configurations together finished in about 1.5 days of cluster time. Everything in this section is span≤20 only — full Logan, the calculator and trends' other option, hasn't been built or queried for real at any scale yet.
